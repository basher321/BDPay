BDPay production runbook (spec 15)
===================================

You run every step below by hand, in order, in Windows PowerShell from D:\BDPay unless a step says otherwise.
Claude Code never runs these commands. No step deletes data.

BEFORE YOU START
- tests/e2e/E2E_CHECKLIST.txt (spec 14) is complete: A-P PASS or documented and fixed.
- Specs 09, 10, 10a, 11, 12 and 12a are built and pass locally (`supabase test db` included); the real
  rate limiter of spec 09 exists (the health function needs it).
- Accounts: Supabase (paid plan), Resend, Cloudflare (with your BDPay domain added), Shopify Partner.
- From the staging project, note the DIGESTS (not values) of PAY_TOKEN_SECRET, CRON_SECRET and SHOPIFY_API_SECRET:
      supabase secrets list --project-ref <staging-ref>
  Production must never show the same digests (step 3 and step 7 checks).
- Never reuse anything from staging: no secret, no Shopify app, no Pages project, no keystore, no database.
- Secrets go ONLY into a hidden prompt in this terminal, `supabase secrets set`, Dashboard > Vault, Resend or the
  Supabase dashboard fields. Never into a file, never typed after "=" on a command line.
- Use ONE PowerShell window for steps 2-9 and do not close it.

Paste these helpers into that window first (they only define functions; nothing runs):

    function Read-Secret([string]$Prompt) {
      $s = Read-Host -AsSecureString $Prompt
      [Net.NetworkCredential]::new('', $s).Password
    }
    function New-RandomSecret {
      $b = New-Object byte[] 32
      $r = [Security.Cryptography.RandomNumberGenerator]::Create(); $r.GetBytes($b); $r.Dispose()
      [Convert]::ToBase64String($b)
    }
    function Set-ProdSecret([string]$Name) {
      $v = Read-Secret $Name
      supabase secrets set "$Name=$v" | Out-Null
      Remove-Variable v
    }

<ref> = the production project reference (dashboard URL after /project/). <domain> = your BDPay domain.
Neither is a secret.

STEP 2 - Link, push the migrations, load the SMS rules
-------------------------------------------------------
This folder must not still be linked to staging:

    Test-Path supabase\.temp\project-ref
        (must print False; if True run `supabase unlink` first)
    supabase link --project-ref <ref>
        (type the database password at the prompt; never use -p)
    supabase db push
        (never add --include-seed)

Load the latest SMS rules (Dashboard > Project Settings > API Keys > service_role > Reveal > copy):

    $env:SUPABASE_URL = "https://<ref>.supabase.co"
    $env:SUPABASE_SERVICE_ROLE_KEY = Read-Secret "production service_role key (paste, Enter)"
    echo $env:SUPABASE_URL
    deno run --allow-net=<ref>.supabase.co --allow-env=SUPABASE_URL,SUPABASE_SERVICE_ROLE_KEY --allow-read=supabase/functions/_shared/parser_rules.json supabase/scripts/load_parser_rules.ts
    Remove-Item Env:SUPABASE_SERVICE_ROLE_KEY, Env:SUPABASE_URL

Then Dashboard > Advisors: run both again; fix every ERROR (RLS on every table is part of spec 12).
check: `supabase projects list` marks bdpay-prod as linked; `supabase migration list --linked` shows every local
migration under "Remote"; the script printed "<version> loaded" with the same version as staging's last load;
both advisors show no ERROR.

STEP 8 - Release keystore (once; keep it forever)
--------------------------------------------------
WARNING: losing this keystore (or its password) means every merchant must uninstall and reinstall BDPay to get
any later update. Keep it outside the project, outside OneDrive / Google Drive / Dropbox, plus offline backups.

keytool comes with Android Studio (adjust the path if yours differs):

    $keytool = "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe"
    New-Item -ItemType Directory -Force D:\bdpay-keys | Out-Null
    & $keytool -genkeypair -v -keystore D:\bdpay-keys\bdpay-release.jks -storetype PKCS12 -keyalg RSA -keysize 4096 -validity 10000 -alias bdpay
        (type the password at its prompts - never -storepass / -keypass on the command line; answer the
         name questions with your business details)

Write android/key.properties by hand in Notepad (never with a command that holds the passwords):

    notepad D:\BDPay\app\android\key.properties
        storeFile=D:/bdpay-keys/bdpay-release.jks
        storePassword=<the keystore password>
        keyAlias=bdpay
        keyPassword=<the same password (PKCS12 uses one password)>

The project folder must not be in a cloud-synced folder while key.properties exists (it holds the password).
Back up D:\bdpay-keys\bdpay-release.jks to two offline USB drives kept in different places; the password goes in
your password manager.
The staging keystore (D:\bdpay-keys-staging\, spec 14 runbook step 9) is a different file: before every
production build open key.properties and check storeFile names D:/bdpay-keys/bdpay-release.jks.
check: `& $keytool -list -v -keystore D:\bdpay-keys\bdpay-release.jks -alias bdpay` (password at the prompt) shows
alias bdpay; write its "SHA256:" certificate fingerprint (public, not secret) into ops/release_checklist.txt;
both USB copies open with the same command.


STEP 9 - Build, publish, announce the version
----------------------------------------------
    cd D:\BDPay\app
    $anon = Read-Secret "production anon key (paste, Enter)"
    flutter build apk --release --obfuscate --split-debug-info=build/symbols --dart-define=SUPABASE_URL=https://<ref>.supabase.co --dart-define=SUPABASE_ANON_KEY=$anon --dart-define=SITE_URL=https://pay.<domain>
    Remove-Variable anon

Keep the symbols privately (they are needed to read crash traces; `flutter clean` would remove them):

    New-Item -ItemType Directory -Force D:\bdpay-release\1.0.0 | Out-Null
    Copy-Item -Recurse build\symbols D:\bdpay-release\1.0.0\symbols

Size and hash (Cloudflare Pages allows at most 25 MiB per file):

    $apk = "build\app\outputs\flutter-apk\app-release.apk"
    [math]::Round((Get-Item $apk).Length / 1MB, 1)
    Get-FileHash -Algorithm SHA256 $apk
        (if the size is 25 or more, build again with --split-per-abi added and publish
         build\app\outputs\flutter-apk\app-arm64-v8a-release.apk instead; hash and size of that file)

Certificate (apksigner is in the Android SDK build-tools folder):

    & "D:\tools\android-sdk\build-tools\<version>\apksigner.bat" verify --print-certs $apk

Copy the APK as bdpay-1.0.0.apk into $dst (step 6 folder); in $dst\download.html set REPLACE_ME_VERSION = 1.0.0,
REPLACE_ME_SIZE = the size in MB, REPLACE_ME_SHA256 = the hash, REPLACE_ME_APK_FILE = bdpay-1.0.0.apk; upload $dst
again as a new deployment of bdpay-pay-prod.

    cd D:\BDPay
    supabase secrets set LATEST_APP_VERSION=1.0.0 APP_DOWNLOAD_URL=https://pay.<domain>/download.html
    supabase unlink

check: apksigner's "SHA-256 digest" of the signer certificate equals the production fingerprint from step 8
(never the staging one); https://pay.<domain>/download.html shows 1.0.0, the size and the hash; a file
downloaded from that page gives the same Get-FileHash value; Test-Path supabase\.temp\project-ref -> False.


STEP 10 - Monitoring
---------------------

alerts to your email and phone app:
  1. HTTPS keyword monitor: https://<ref>.supabase.co/functions/v1/health, keyword "db":true
  2. HTTPS monitor: https://pay.<domain>/
No key or token goes into the monitor.
Weekly: run ops/e2e_queries.sql in the SQL Editor (verification times, heartbeat gaps, rejected SMS, order syncs,
open alerts).
Test alert email (plan 15 D225): with your own store connected and your own phone signed out for 35 minutes, a
noActiveDevice alert opens and emails you (or switch the signed-in phone off for 16 minutes: phoneSilent).
check: both monitors show "Up" and their test notification reached you; the test alert email arrived from
alerts@mail.<domain>.
